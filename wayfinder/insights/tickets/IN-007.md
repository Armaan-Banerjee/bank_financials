## Question

Build a refreshable SQLite database from the insights project's current
normalized data — IN-001's `research/bank_metrics.csv` and IN-002's
`research/bank_parent_groups.md` — as a validated, standalone artifact.

**Scope note (split 2026-08-29 at the user's request, from the original
IN-007 which bundled this with migrating consumers):** this ticket is
build-and-validate only. It does NOT touch `scripts/cluster_banks.py`, this
map's Notes, or any other existing script/doc that currently reads the CSV/
markdown outputs — those stay exactly as they are and remain the source of
truth consumers actually use. Migrating anything to read from the database
this ticket produces is [IN-008](IN-008.md)'s job, not this one's. Think of
this ticket as "prove the database is right," not "cut over to it."

This remains on the insights map for now because its scope is a data
foundation for IN-003 onward. Create a separate map only if the work expands
into a wider enterprise data platform, multi-user service, or production
deployment project.

**Forward note**: the user has decided (see IN-008) that the database will
become the actual source of truth, with the CSV/markdown regenerated FROM
it rather than the other way around - that inversion is explicitly IN-008's
job, not this ticket's. This ticket's one-off import (CSV/markdown → DB) is
still the right first step; just don't be surprised that the direction
flips immediately afterward.

## What to produce

- A re-runnable database-build script under `scripts/` (e.g.
  `scripts/build_insights_db.py`) using the standard library `sqlite3`
  module where practical.
- A durable database under `research/` (e.g. `research/insights.db`), with a
  documented schema covering at minimum:
  - bank/legal-entity nodes and stable FRNs;
  - canonical and source filename names;
  - annual metric observations, preserving raw values, parsed numeric
    values, units, years, workbook kind, and basis notes;
  - parent/intermediate/ultimate nodes and typed, effective-dated graph
    edges from IN-002;
  - source/provenance references and refresh metadata (which CSV/markdown
    generation the DB was built from, and when).
- Primary keys and uniqueness constraints that make FRN the stable bank join
  key, while retaining readable names for display. IN-001's own recent
  switch to FRN as its internal identity key (see its ticket's session log)
  is the same principle applied one layer down — reuse it, don't re-derive.
- Import validation showing that all 145 built banks and all 145 FRNs are
  represented, annual metric row counts agree with IN-001 after
  deduplication (12,846 rows as of IN-001's last run — re-check against
  whatever `research/bank_metrics.csv.schema.json` reports at build time,
  not a hardcoded number), and parent-map rows join without a name
  crosswalk (per IN-002's own FRN-column fix).
- A short schema note (tables, columns, keys) documenting the database
  itself — not a migration guide for existing tooling, that's IN-008.

## Constraints

- Do not modify bank workbooks.
- Do not modify `scripts/cluster_banks.py` or any other existing consumer -
  out of scope, see IN-008.
- Preserve missing values as NULL, never zero.
- Keep legal ownership and regulatory consolidation as separate edge types.
- Keep interim disclosures out of the initial annual database load; design
  the schema so they can be added later.
- Preserve currency, reporting-basis, restatement, and source-citation
  information rather than flattening it away.
- The CSV and markdown outputs remain fully authoritative and unchanged by
  this ticket - the database is a new, additional artifact until IN-008
  decides otherwise.

## Progress

Built `scripts/build_insights_db.py` and `research/insights.db`. Neither
`research/bank_metrics.csv` nor `research/bank_parent_groups.md` was
modified (confirmed via mtimes before/after the run) - this ticket is
strictly a reader of both, as scoped.

**Schema** (5 tables, detailed in the script's own docstring):
`banks` (one row per FRN), `annual_metrics` (mirrors IN-001's own
`(frn, sheet, row_label, year)` identity key exactly, `UNIQUE` constraint
enforced at the DB level too), `parent_group_lookup` (IN-002's bank-level
table), `parent_group_edges` (IN-002's typed edge list, with best-effort
`from_frn`/`to_frn` resolution against known banks - many edge endpoints
are parent/holding entities like "HSBC Holdings plc" that aren't themselves
one of the 145 built banks, so those stay unresolved by design, not by
bug), and `refresh_metadata` (one row: build timestamp, source paths, the
source CSV's own schema version and row count, output counts).

**Validation, run automatically by the script on every build** (all passed):
145 banks / 145 distinct FRNs; 12,846 `annual_metrics` rows, matching
`bank_metrics.csv.schema.json`'s `row_count` exactly (read dynamically, not
hardcoded); 0 duplicate identity keys; 0 orphaned metric rows; all 145
`parent_group_lookup` rows join to `banks` by FRN with zero crosswalk
needed (this is the whole point of IN-002's own FRN-column fix); 0 rows
with a numeric value but a null raw value (missing-value fidelity check).
Also spot-checked manually: the Barclays Bank Plc/Barclays Bank UK PLC
sibling pair resolve to their correct distinct FRNs and rows in `banks`,
and the HSBC group's 4 entities all resolve to the same `ultimate_group`.

The build is fully idempotent/re-runnable: it drops and recreates only its
own database file (removing any prior `research/insights.db` first, and
cleaning up a half-built file if validation ever fails mid-build), never
touching the CSV/markdown inputs or any other project file.

Per this ticket's scope, `scripts/cluster_banks.py` and everything else in
the project is completely untouched and keeps reading the CSV/markdown as
before - IN-008 is unblocked to do that migration.
