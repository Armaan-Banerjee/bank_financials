## Question

A 2026-09-01 aggressive read-only code audit (5 parallel reviews of the whole
`scripts/insights/` codebase) found that `analyze_trends.py`'s `extract()`
(lines ~27-41, 91-130) is a **fourth** independent implementation of
"pick the right row per bank/period," alongside the three already found and
unified onto `in009_analysis.py`'s canonical `_select_metric_observations()`
(the Barclays 56465% fix, the second leverage-ratio fix, and IN-028's two
further bugs). Unlike those, `analyze_trends.py` never adopted
`_is_percent_value()` or any percent-vs-absolute guard at all — it relies
solely on regex label matching plus a small hand-curated `excluded` substring
list per metric. For NSFR specifically: `pattern = NSFR|stable funding ratio`
(unanchored `re.search`) matches ANY label containing "NSFR" anywhere, and
`excluded = ("available stable", "required stable")` only catches two
specific phrasings — a supporting absolute row phrased differently (e.g.
"NSFR eligible liabilities (£m)") would match the pattern, evade the
exclusion list, and get selected as if it were the ratio.

**This is live-consumer code, not a dormant path**: `extract()`'s output
feeds `pairwise_counts()`, which `build_in005_prototype.py` uses directly for
`trend_series` — the selectable metric dropdown in the HTML deliverable's
"Trend Signals" chart, including LCR and NSFR.

**Not yet confirmed** whether a bad value currently surfaces from this in the
live 145-bank dataset (the audit found the structural gap by reading the
code, not by re-running it against real data) — verifying that against
`insights.db` is the first thing whoever picks this up should do, before
assuming the fix is purely precautionary.

## Related findings from the same audit — same root pattern, fold into this ticket

- **`in020_regulatory_context.py`'s `match_context()` (line ~40)** picks one
  arbitrary regulatory-context record (`next(item for item in candidates if
  item["value"] is not None)`) instead of summing minimum+buffer the way
  `in021_headroom_trajectory.py`'s `applicable_context()` correctly does for
  the same `CONTEXT` table. Currently dormant/unreachable only because
  `reporting_basis` is NULL for every annual_metrics row (a documented,
  separate known gap) — `match_context()` short-circuits to
  `context_unavailable` before reaching the buggy line. Will silently misfire
  the moment that gap is ever filled. Fix it now while it's cheap to test,
  don't wait for it to become live-visible.
- **`in009_analysis.py`'s `comparison_diagnostics()` strict-mode common-basis
  tie-break (lines ~180-187)** picks the lexically-largest basis string on a
  count tie (`max(bases, key=lambda b: (count, b))`) — same string-sort
  tie-break shape as all three prior confirmed bugs, smaller blast radius
  here (only two possible basis values today) but undocumented and worth
  making an explicit, reasoned tie-break like the rest of `in009`'s selector.
- **`analysis_queries.py`'s `latest_interim_snapshot()` (lines ~110-123)**
  falls back to lexical string comparison of `period_label_raw` when
  `period_end_date` is missing — interim labels use varied real-world formats
  (month names, quarters, halves), so e.g. "December 2023" sorts lexically
  after "November 2024" ('D' > 'N'), meaning this function could pick a
  chronologically-earlier snapshot as "latest." Needs a real date-parsing
  fallback, not lexical string comparison.
- **`extract_metrics.py`'s `deduplicate()` (lines ~613-651)** only checks
  `value_raw` for conflicts when collapsing rows sharing an identity key
  (frn, sheet, row_label, year) — two rows agreeing on `value_raw` but
  disagreeing on `unit` or `reporting_basis` collapse silently to the first
  one with no warning, in a pipeline where wrong unit/basis attribution is
  exactly the field class that has already caused three confirmed bugs.
  Should at minimum warn/log on a unit or basis mismatch even when values
  agree.
- **`export_parent_group_tables.py`'s `_render_lookup_rows`/`_render_edge_rows`
  (lines ~59-78)** build markdown table rows via raw f-string interpolation
  of free-text DB fields (evidence, status_caveat, effective_note) with no
  escaping of literal `|` characters — any such field containing a pipe would
  silently corrupt the regenerated table structure. Not verified against
  current data content; add escaping regardless, it's cheap and this table is
  regenerated on every refresh.

## Scope/seams

- Fix `analyze_trends.py`'s `extract()` first: either route it through
  `in009_analysis.py`'s canonical selector (preferred, avoids yet another
  independent implementation — check whether `extract()`'s
  metric-name-to-sheet mapping and its consumers can tolerate that shape
  change) or, if genuinely structurally incompatible with reuse, add the same
  `_is_percent_value()` guard this file currently lacks entirely. Re-run a
  full 145-bank sweep afterward the same way IN-028's fix was verified.
- Fix the four related findings above at the same time — they're small,
  independent, and share the audit's underlying lesson (duplicated/ad-hoc
  selection and tie-break logic recurring across this codebase).
- Add regression tests for each: an NSFR/LCR-labeled absolute row that would
  have fooled `analyze_trends.py`'s old regex; the in020 minimum+buffer case
  once `reporting_basis` coverage exists (or a synthetic fixture that forces
  it); a basis tie-break case in `in009`; a lexically-out-of-order interim
  date case; a unit/basis-conflicting duplicate row in `extract_metrics.py`;
  a `|`-containing evidence field in `export_parent_group_tables.py`.

## Resolution (2026-09-01)

- `analyze_trends.py`'s `extract()` now applies `in009_analysis.py`'s
  `_is_percent_value()` guard for every `PERCENT_ONLY_SHEETS` metric, so an
  absolute-amount row can no longer evade the regex/`excluded`-list and be
  reported as if it were the ratio. Verified against the live 145-bank
  dataset (`analyze_trends.py` run directly) - coverage counts unchanged
  from before the fix (e.g. CET1 109 banks FY22→23, matching the figure
  already independently confirmed in the 2026-09-01 HTML↔PDF audit), so no
  live-visible bad value existed, but the structural gap is now closed.
- `in020_regulatory_context.py`'s `match_context()` now sums minimum+buffer
  (matching `in021_headroom_trajectory.py`'s `applicable_context()`) instead
  of returning the first matching CONTEXT record - `context_id`/`source`
  are now lists (joined with `; ` for the CSV export) since a match can now
  legitimately span more than one CONTEXT row.
- `in009_analysis.py`'s `comparison_diagnostics()` strict-basis tie-break now
  prefers `entity` over `consolidated_group` on a count tie, via an explicit
  `_BASIS_PREFERENCE` dict, not the basis string's alphabetical order.
- `analysis_queries.py`'s `latest_interim_snapshot()` now parses
  `period_label_raw` via `normalize_period()` for a comparable ISO date when
  `period_end_date` is missing, instead of comparing the raw label lexically.
- `extract_metrics.py`'s `deduplicate()` now raises (same as a value
  conflict) when two rows agree on `value_raw` but disagree on `unit` or
  `reporting_basis`, instead of silently collapsing to the first row.
- `export_parent_group_tables.py`'s markdown-table renderers now escape a
  literal `|` in every free-text DB field.
- Also removed `in009_analysis.py`'s `_metric_observations()` pre-filter
  (required the literal word "ratio" in the label, or excluded any
  "exposure"-labeled Leverage row) - it could silently drop a genuine
  percentage row with atypical phrasing before the real selector ever saw
  it; all 4 call sites (`in009`, `in010`, `in021`) now filter by sheet only
  and rely on the downstream selector's `PERCENT_ONLY_SHEETS` guard.
- Regression tests added for each fix; full suite passes (231 tests at time
  of this ticket's close, up from 228 pre-fix - some of the increase is from
  IN-030's parallel work in the same session). Live `refresh_all.py` runs
  clean.
