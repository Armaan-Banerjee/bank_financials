## Question

A full-pipeline data-correctness review (2026-09-01, five parallel audits: workbook↔DB
extraction, cross-payload consistency, HTML↔PDF consistency, full-dataset anomaly
sweep, pipeline health) found the pipeline overall in very good shape — 219 tests
passing, byte-parity on generated exports, 0 mismatches in workbook→DB extraction,
0 mismatches in HTML↔PDF headline figures, all previously-fixed percent-vs-absolute
bugs (IN-009's Barclays 56465% fix) confirmed still fixed everywhere. But it found
**two new, currently-live data bugs**, both in `scripts/insights/in016_distribution.py`,
both the same root cause as the earlier fix: this script keeps its own independent
"pick one row per bank/period" logic instead of calling `in009_analysis.py`'s
canonical, already-hardened selector — exactly the duplication
`scripts/insights/README.md` already warns against ("Everything else imports from
here rather than re-writing SQL/logic"), and exactly the same pattern that caused
the second leverage-ratio bug fixed 2026-08-30 (see this map's Decisions-so-far).

## Bug 1 — wrong pick between two both-valid percentage rows (ratio sheets)

`distribution_for_metric()`'s and `_canonical_rows()`'s per-FRN "latest observation"
tie-break sorts candidates by `(period_key, str(value_raw))` and takes the lexical
minimum. When a bank discloses two genuinely different, both-valid percentage rows
for the same period (e.g. Santander's leverage ratio "excluding vs including claims
on central banks" — the workbook/deliverable's own "basis" callout says the
excluding-basis figure is the comparable one), this tie-break has no concept of
which is the documented/comparable label and just picks whichever value string
sorts first (`"4.3%" < "5.3%"`) — the same string-sort defect class as the earlier
Barclays fix, but on a case the earlier `_is_percent_value` guard doesn't cover
(both candidates *are* valid percentages here).

**Confirmed live and visibly wrong in the deliverable today**: Barclays Bank UK PLC
FY2021 leverage ratio shows **5.6%** in the trajectory/headroom sections (which use
`in009`'s selector) but **4.1%** in the distribution-benchmarks section (`in016`,
and `in023_distribution_visuals.json` which is built FROM `in016`) — two different
values for the same bank/year in two different parts of the same page.

21 (bank, metric, year) cells confirmed affected — 19 on Leverage Ratio, 2 on MREL
Ratio (full list logged in the audit transcript this ticket was opened from; ask
the driving session if the list isn't reproduced in a later ticket update). Affects
`in016_distribution.json`'s `distributions` (broad + strict) and, downstream,
`in023_distribution_visuals.json`. `rank_movement`/`_exact_cohort` in `in016` uses
the identical tie-break pattern and is presumably affected for the same
banks/years, though not individually re-verified — check it as part of this fix.

## Bug 2 — inconsistent row choice across years for the same bank/absolute-metric series

Kingdom Bank Limited's "Total Capital" (absolute, `£'000`) in
`in016_distribution.json`'s `absolute_distributions` selects a different row
definition depending on year: FY2021/FY2024/FY2025 pick
`"Shareholders' funds (Core Equity Tier 1)"` (7451 / 15512 / 15808), while
FY2022/FY2023 pick `"Total regulatory capital (CET1 + Tier 2)"` (10053 / 10576) —
a different row that includes the ~£700-761k Tier 2 subordinated-liabilities
component the other years' pick excludes. All three candidate rows are present,
`annual_eligible`, and otherwise identically-statused for all 5 years, so this is a
selection inconsistency, not a missing-data artifact. Swept across all 145 banks ×
4 absolute metrics (CET1 Capital, Tier 1 Capital, Total Capital, Total RWAs) —
Kingdom Bank/Total Capital is the only instance found, but the underlying
selection code that produced it is shared across all four absolute metrics and all
145 banks, so treat this as "the mechanism is unsound," not "one bank is wrong."

**Impact**: any year-over-year trend, distribution percentile, or absolute-analysis
cohort placement computed for Kingdom Bank's Total Capital mixes two different
metric definitions, understating it in 3 of 5 years.

Cross-checked against `in009_analysis.py`'s current `_select_metric_observations`/
`_label_sort_key` (lines ~260-309 as of 2026-09-01): as written, that function
deterministically picks the same primary label every year for a given bank/sheet
(tie broken once, outside the per-year loop) — so `in016`'s absolute-metric path
has its own independent, not-yet-reconciled selection logic here too, same as
Bug 1's ratio-sheet path.

## Scope/seams

- Do not patch `in016_distribution.py`'s tie-break heuristics again in place — that
  is what produced the first fix (which didn't cover this case) and the second fix
  (`_is_percent_value`, which also didn't cover this case, since both bugs found
  here involve two *equally valid* candidates, not a percent-vs-absolute
  confusion). The recurring lesson across three bugs now is that **duplicated
  selection logic is the actual defect**, not any one heuristic within it.
- Preferred fix direction (confirm against the current code before committing):
  have `in016_distribution.py` call `in009_analysis.py`'s existing selector
  (`_select_metric_observations`/`build_metric_series`, extended if needed to
  cover absolute metrics, not just `PERCENT_ONLY_SHEETS`) directly for both its
  ratio-distribution path and its absolute-distribution/rank-movement path,
  rather than maintaining `_canonical_rows()`/`distribution_for_metric()`'s and
  the absolute-metric path's own selection logic. If `in009`'s selector doesn't
  yet have a sane, tested tie-break for "two both-valid percentage variants for
  the same period" (basis-preference, not string-sort), that tie-break needs to
  be added there once, in the canonical location, not reinvented per-caller.
  Check `in022_ratio_decomposition.py`, `in024_trajectory.py`, and
  `in025_quality_views.py` too — they were built after the first fix landed, but
