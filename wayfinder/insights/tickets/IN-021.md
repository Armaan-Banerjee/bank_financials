## Question

Build a headroom-trajectory analysis: for each bank/metric pair with a
regulatory minimum in IN-020's context table, combine the bank's current
buffer above that minimum with its recent multi-year trend direction and
magnitude (already computed by IN-009) to flag entities whose own trajectory
is eroding headroom fastest — a forward-looking "which banks are trending
toward their regulatory floor" screen, not just a snapshot of where they
stand today or how they compare to peers at one point in time.

**Why this is genuinely new, not a restatement of an existing ticket** (checked
against `scripts/insights/README.md` and the source of IN-009, IN-012, IN-016,
IN-017, IN-018, IN-019, IN-020 before writing this):

- IN-009 computes trend direction/magnitude per metric but never relates it to
  a regulatory minimum.
- IN-020 attaches a static regulatory minimum/buffer value to an observation
  but never looks at trend — it's a point-in-time context label, not a
  trajectory.
- IN-016 computes distributional rank/percentile position among peers at a
  fixed year, not movement over time relative to a floor.
- IN-012 covers absolute/size-aware capital and RWA levels, not ratio
  trajectory against a regulatory threshold.
- None of the above, nor `analysis_queries.py` (IN-013), compute or expose a
  "current headroom minus trend-implied erosion" figure. This is the one
  analytical angle - the kind of leading-indicator/early-warning view a
  PowerBI or similar risk dashboard would build from data that already looks
  like this - that the map doesn't yet cover.

## Scope/seams

- **Headroom calculation**: for each (bank, metric, latest comparable year)
  pair that both IN-009's normalized series and IN-020's regulatory context
  cover, compute `latest_value - applicable_minimum` (minimum + any
  applicable buffer, matched the same safe way IN-020's `match_context()`
  already does - do not loosen that matching policy to manufacture more
  coverage).
- **Trend-implied trajectory**: reuse IN-009's existing pairwise trend/movement
  computation (`pairwise_trend`, `_trend_rows`) rather than re-deriving trend
  math independently. Require a minimum number of comparable year-pairs
  (mirror IN-009's existing insufficient-evidence guard) before calling a
  trajectory "declining" - insufficient evidence must produce an explicit
  `insufficient_evidence` status, never a silently-guessed direction.
- **Projection discipline**: this is a screen, not a forecast. Do not
  extrapolate a numeric future value or a "breach by year X" date - the
  underlying panel is annual, sparse for some banks/metrics, and several
  known basis/restatement quirks (see the map's Notes) make naive
  extrapolation actively misleading. Score and rank by trend magnitude and
  current headroom only; leave date/value projection out of scope for this
  ticket (note it in the ticket as possible future fog if it turns out to be
  wanted).
- **Output**: a new `in021_headroom_trajectory.py` producing a JSON payload
  (mirror IN-009/IN-016's shape and file-naming convention) with one record
  per screened (bank, metric) pair: current value, applicable minimum,
  current headroom, trend direction/magnitude, comparable-year count, and an
  explicit status (`screened` / `insufficient_evidence` / `no_regulatory_context`).
  Follow `CODING_STANDARDS.md`: no hardcoded per-bank figures, NULL (not
  zero/guessed) for anything unresolvable, validated against the DB the same
  way `validate_cluster_inputs()` guards staleness elsewhere.
- **Deliverable integration (HTML + PDF)**: unlike the IN-009→IN-011 and
  IN-012→IN-014 precedent of a separate follow-on ticket, this ticket carries
  its own integration into `build_in005_prototype.py` (HTML) and
  `build_in006_pdf.py` (PDF) - the user wants the headroom-trajectory screen
  visible in both deliverables, not just produced as a standalone JSON file.
  Follow the existing integration pattern from IN-011/IN-014: the deliverable
  generators consume the shared JSON payload (never re-derive the
  headroom/trend numbers themselves), both generators call
  `validate_cluster_inputs()`-style staleness checks against this new output,
  and any new section must not leak internal ticket IDs or debug strings into
  client-facing text (mirror `test_pipeline.py`'s existing
  `assertNotIn("IN-009", pdf_text)`-style guard for whatever this ticket adds).
  `insufficient_evidence`/`no_regulatory_context` rows must render as visible,
  explicit "not enough data" states in both deliverables, never be silently
  dropped from the section.
- **Tests**: unit tests for the headroom/trend-combination logic (including
  the insufficient-evidence and no-context guard paths); a
  `test_pipeline.py`-style subprocess check that the script runs cleanly
  against a real refreshed database; and `test_pipeline.py` assertions that
  the HTML and PDF outputs both contain the new section, that
  insufficient-evidence banks render an explicit state, and that no internal
  ticket IDs/debug strings leak into either deliverable. Add the script to
  `refresh_all.py`'s `STEPS` (after `in009_analysis.py` and
  `in020_regulatory_context.py`, its two dependencies, and before the two
  `build_in00{5,6}` deliverable steps) once it's built, and to
  `scripts/insights/README.md`'s file table.
