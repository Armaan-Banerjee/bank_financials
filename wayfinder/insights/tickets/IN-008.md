## Question

Once IN-007's database exists and is validated, migrate the project onto it
as the actual source of truth: `research/insights.db` becomes what every
refresh writes to and what every consumer reads from; `research/
bank_metrics.csv` and `research/bank_parent_groups.md` become **generated
exports of the database**, not independently-maintained files. This was an
open decision when this ticket was created — **settled by the user
(2026-08-29): database as source of truth, CSV/markdown generated from it,
not the other way around.**

**Scope note:** split out of the original IN-007 (2026-08-29, at the user's
request) specifically so migration work — which touches things that are
already working, like `scripts/cluster_banks.py` — doesn't get bundled with
and block on the lower-risk database-build work. This ticket is the risky
half; take more care here than IN-007 needed.

## What to produce

- **Refresh path inverted**: `scripts/extract_metrics.py` (IN-001) and
  whatever script/process produced `research/bank_parent_groups.md`
  (IN-002) must write to `research/insights.db` as their primary output
  going forward, with the CSV and markdown files regenerated FROM the
  database (a small export step) rather than built independently. This is
  what makes the database an actual source of truth rather than a one-off
  IN-007 snapshot that immediately goes stale on the next refresh.
- Update `scripts/cluster_banks.py` to read from the database directly,
  preserving its existing CLI/output shape so downstream tickets (IN-004,
  IN-005, IN-006, or a rerun of IN-003 itself) aren't broken by the switch.
  Rerun it after migrating and confirm the clustering result is unchanged
  from IN-003's original run (same 95/18 split, same silhouette score) - a
  behavior-preserving migration, not a re-derivation.
- Update `../map.md`'s Notes to name the database as the primary dataset for
  any future ticket on this map, noting that the CSV/markdown remain
  available as generated exports (useful for a quick look or a spreadsheet
  hand-off) but are no longer hand-authoritative.
- Update IN-001's and IN-002's own ticket files (Progress/Session log,
  briefly) to note the refresh path changed, so a future session reading
  those tickets for context isn't misled into thinking the CSV/markdown are
  still the primary write target.

## Constraints

- Do not start until IN-007 is closed and its validation numbers check out -
  migrating consumers onto an unvalidated database risks propagating a
  schema bug silently into every downstream ticket.
- **Consider waiting until IN-004, IN-005, and IN-006 have closed before
  claiming this ticket**, even though it isn't formally blocked on them.
  Those tickets are actively building the client deliverable against the
  CSV/markdown right now (per the map's ticket index at the time this
  ticket was written) - migrating the underlying data source out from under
  them mid-build risks real churn for no benefit to the client deliverable
  itself. This is guidance for whoever claims the ticket to weigh against
  the map's live state, not a hard `blocked_by` edge, since making it a hard
  block could stall the database work indefinitely if IN-004/005/006 run
  long.
- The CSV/markdown export step must reproduce byte-for-byte-equivalent
  content (same columns, same row shape) to what IN-001/IN-002 produced
  directly, so nothing downstream that still reads the exported files
  breaks silently.

**What changed**:
1. `scripts/build_insights_db.py` refactored from a single `build()`
   function into reusable pieces: `write_banks_and_metrics(conn, rows, ...)`
   and `write_parent_group(conn, lookup_rows, edge_rows)`, each owning only
   its own tables (independently refreshable - discovered and fixed a real
   bug here: an initial DROP+CREATE approach with `PRAGMA foreign_keys=ON`
   failed with `FOREIGN KEY constraint failed` on the very first rebuild,
   since parent_group_lookup/edges reference banks(frn); fixed by dropping
   the FK-enforcement pragma and relying on `validate()`'s explicit
   Python-level orphan checks instead, since the two halves are legitimately
   refreshed independently and enforcing FK integrity at write time doesn't
   fit that). Also fixed a real row-ordering bug: the lookup table's rows
   aren't strictly case-insensitive-alphabetical throughout, so `ORDER BY
   bank_name` in SQL produced a different (still plausible-looking) order
   than the source file - added an explicit `sort_order` column that
   preserves the source file's exact row order instead of re-deriving one.
   The standalone CLI (`python3 scripts/build_insights_db.py`, full rebuild
   from CSV+markdown) still works, for disaster recovery.
2. `scripts/extract_metrics.py`'s only change: its final write step now
   writes to `research/insights.db` first, then exports the CSV by reading
   it back FROM the database (`export_metrics_csv`), instead of writing CSV
   independently from the same in-memory rows. Zero changes to extraction,
   deduplication, or warning logic.
3. New `scripts/export_parent_group_tables.py`: imports the markdown's two
   tables into the database, then regenerates and splices them back into
   the file in place (see the scope decision above).
4. `scripts/cluster_banks.py`: added `load_rows_from_db()`, returning rows
   shaped identically (same keys, same string typing) to the existing CSV
   loader, so `build_feature_matrix()` - the actual clustering-relevant
   logic - needed zero changes. `--db` (default `research/insights.db`) is
   now the default source; `--in <csv>` remains as an explicit fallback.
