## Question

The user reported the live HTML dashboard "seems to have broken" - only the
sidebar rendered, and the search box did nothing. Diff-testing confirmed this
was not caused by IN-033's edits (identical output with/without them). The
real cause: `wayfinder/insights/deliverable/uk_bank_insights.html` was
131.7MB, of which 124MB was the `const D={...}` payload embedded in a
`<script>` tag. A browser loading that much inline JSON before any of the
dashboard's population JS can run is consistent with exactly what was
reported - a static sidebar with nothing else ever rendering.

Traced the payload's `D.in011` (126.4MB) breakdown to two independent bugs,
neither related to any of IN-029 through IN-033's fixes:

1. **`build_in023_payload()` embeds full copies of `in016` and `in017`
   wholesale** inside its own returned dict, and `build_in011_payload()` then
   stores that embedded copy on top of `in016`/`in017` already being present
   as siblings. `in011.in023` was 45.6MB, of which ~45.1MB was this exact
   duplicate. Nothing ever reads `in023["in017"]` at all (grepped); the HTML/
   PDF renderers only ever read `in023["in016"]["distributions"]`.
2. **`in016`, `in017["lineage"]`, and `in025["trace"]` are large aggregate/
   raw-observation payloads that only the server-side HTML/PDF renderers
   consume (to pre-render static tables/SVGs at build time) - no client-side
   JS in `build_in005_prototype.py` ever references `D.in011.in016`,
   `D.in011.in017.lineage`, or `D.in011.in025.trace`** (confirmed by grep -
   only the small `trace_completeness` summary and, for lineage, the first 8
   rows are ever read). Embedding them in full in the client payload was pure
   dead weight: `in016` alone was 12.7MB, `in017.lineage` was ~32.3MB of
   `in017`'s 32.4MB, `in025.trace` was 32.3MB of `in025`'s 33MB.

## Resolution (2026-09-01)

- `in011_deliverables.py`'s `build_in011_payload()` no longer embeds full
  `in016`/`in017` copies inside `in023` - keeps only `in023`'s own
  `metadata`/`coverage`. `render_html_distribution_visuals()` now takes
  `in016` as an explicit second argument (sourced from the sibling `in016`
  key) instead of reaching into `in023["in016"]`; `render_pdf_analysis_lines()`
  reads `payload["in016"]["distributions"]` the same way. `in017["lineage"]`
  is truncated to the first 8 rows (the only rows any renderer reads) before
  being embedded in `in011`'s returned dict - the full `lineage` remains
  available in full via the *standalone* `in017_quality.json` artifact
  `refresh_all.py`'s own `in017_quality.py` step still writes independently
  (per that module's own "intentionally retained for Power BI and audit
  tooling" docstring - unaffected, since that step calls
  `build_in017_payload()` directly, not through `build_in011_payload()`).
- `build_in005_prototype.py` now renders `analysis_html` (which needs the
  full `in016` and `in025["trace"]`) *before* building the client JSON
  payload, then drops `in011["in016"]` entirely and pops
  `in011["in025"]["trace"]` before the `json.dumps()` call that embeds `D` -
  same "render first, strip before serializing" pattern applied twice.
- Regression test added to `test_pipeline.py`'s full end-to-end pipeline test:
  asserts `in016`/`in017` are absent from the client payload's `in023`, `trace`
  is absent from its `in025`, and the whole deliverable HTML stays under
  35MB - a generous ceiling well above the ~11MB the fix actually produces,
  but tight enough to catch this exact bug class regressing.
- Net effect on the live deliverable: **131.7MB -> 11.1MB (91.5% smaller)**.
  Verified nothing was lost in the process: all 6 embedded `<script>` blocks
  still pass `node --check`; every HTML tag type (`section`/`div`/`article`/
  `aside`/`table`) still balances open/close counts exactly as before; every
  previously-verified CSS rule (watchlist, freshness badge, sparkline, global
  search) is still present exactly once; the server-rendered "Robust
  distributions", "Sample source trace", and "Bank × metric × year evidence
  coverage" sections are all still present with real content. PDF deliverable
  regenerates cleanly with its live-computed cover date unaffected (uses a
  separate `build_in011_payload()` call in `build_in006_pdf.py`, untouched
  by any of this).
- Full suite: 231 tests passing; live `refresh_all.py` clean.
